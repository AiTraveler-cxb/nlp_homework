# 实验报告：让 LLM 编写 Skill 并自行优化 —— 前后效果量化对比

> 该作业的**结果类文档示例**（作业要求：让大模型编写一个 Claude Code 原生 skill，再让它多目标优化，用量化指标对比优化前后效果）。
>
> **数据声明**：本文档中的 token / 耗时 / 质量数据为**教学示意值**（按真实的优化机理与合理量级虚构），用于展示"一份合格的实验结果文档长什么样、该怎么分析和归因"。真实数据须学生自己在固定模型上按一致协议跑出后替换：多个固定基准用例 × 多次重复，每次用**全新会话**（冷缓存），从会话日志解析每次 API 调用的 token usage 与工具步数，端到端耗时用秒表计时。**替换前请删除本声明。**
>
> 示例任务：`code-metrics` skill —— 输入一段 Python 代码，输出含 `行数 / 圈复杂度 / 未使用变量` 的 Markdown 报告。

---

## 1. 一句话结论

对同一个任务，让 LLM 先"写出"一个 skill（v1），再把 v1 连同实测数据喂回去让它"多目标优化"（省 token / 更快 / 质量不降），得到 v2。

- 每次运行的**输入 token 中位下降 45%**（12,940 → 7,120），估算**单次运行成本下降约 26%**，端到端**耗时下降约 41%**（21.3s → 12.6s）；
- 质量**未回退**：15/15 用例通过，平均分 0.987 → 0.973（在预设容差 0.02 内）；
- 最大功臣是**精简 SKILL.md 正文 + 把背景知识下沉到 references（用到才读）**，而非"少干活"式的取巧。

## 2. 实验设计

### 2.1 任务与 skill

| 项 | 内容 |
|---|---|
| skill 名 | `code-metrics` |
| 输入 | 一段 Python 代码文件路径 |
| 输出 | Markdown 报告：总行数、圈复杂度、未使用变量列表，三类指标**数值准确** |
| skill 结构 | `SKILL.md`（frontmatter+触发+流程）+ `scripts/metrics.py`（一次 AST 扫描算全三指标） |
| 质量基准 | 3 个固定代码用例（含故意埋点：2 个未用变量、1 个高复杂度函数、若干空行干扰），与 `expected/*.expected.json` 比对：三字段全对 score=1，每错一个扣 0.2；`pass` 阈值 score≥0.9 |

### 2.2 评测协议

- 3 个 case × 5 次 = **15 个样本/版本**；
- 每次运行都是**全新 headless 会话**（冷会话，缓存口径一致），固定同一模型；
- 只统计"检测到 `Skill` 工具被调用"的运行（否则是裸模型硬答，已全部触发）；
- 指标口径：
  - **token**：从会话日志解析每次 API 调用的 `input_tokens` / `cache_creation_input_tokens`(写缓存) / `cache_read_input_tokens`(读缓存) / `output_tokens`，分项累计，另给 total；
  - **执行效率**：`wall`=进程端到端秒数（秒表），`turns`=带 usage 的 assistant 消息数（≈API 轮数），`tool_calls`=全部工具调用次数；
  - **质量**：`pass_rate`、`avg_score`。
- 汇总取**中位数**为主，辅以均值±std。

## 3. v1（LLM 首写版本）：怎么生成、贵在哪

**生成方式**：把需求书写进 prompt（触发场景、产物规范、质量硬指标、执行约束：必须含 SKILL.md+可执行脚本、正文精简、脚本健壮），让 Claude 写入项目 `.claude/skills/code-metrics/`，手跑 1 个 case 验证后快照为 `v1/`。

**v1 的三个"贵"点**（人工读代码诊断，非事后诸葛）：
1. **SKILL.md 正文臃肿**：约 480 词，把"什么是圈复杂度、怎么数"整段背景写进正文 —— 每次运行都被当成上下文送进模型；
2. **读取习惯差**：每次开工先 `Read` 一份大 reference 再动手；数指标时分多次小工具调用（先数行、再数圈复杂度、再找未用变量），来回路程多；
3. **输出靠追问**：先给个草稿格式再问"这样可以吗"，额外多 1~2 轮。

### baseline（v1）原始数据

| 指标 | 中位数 | 均值±std | 说明 |
|---|---|---|---|
| input tokens | 12,940 | 13,120±860 | 每次运行真正"新想"的输入 |
| cache_read tokens | 1,850 | 1,790±210 | 命中 prompt 缓存的读取 |
| cache_write tokens | 1,610 | 1,580±150 | 写缓存（系统/技能前缀等） |
| output tokens | 1,740 | 1,820±240 | 生成内容 |
| **total tokens** | **18,140** | 18,420±980 | 四项之和 |
| wall（秒） | 21.3 | 21.8±2.4 | 端到端 |
| turns | 9 | 9.0±1.1 | ≈API 轮数 |
| tool_calls | 16 | 15.8±2.0 | 含 Skill 自身 1 次 |
| 质量 | 15/15 | avg 0.987 | 全部达标 |

## 4. 优化环节

**优化 prompt（摘要）**：明确"这是优化不是重写"；保留任务与产物规范；三个目标必须同时满足（1）token 更省：精简正文、冗余下沉 references、减少来回、能一次算完不分多次；（2）更快：减少耗时与步数、脚本做性能优化；（3）质量不降：不得删校验/输出字段；禁止用"少干活"取巧；输出改动清单+理由+自评收益。

### v2 改动清单与归因

| # | v2 的改动 | 模型自述预期收益 | 实测归因（人工复核） |
|---|---|---|---|
| 1 | SKILL.md 正文 480→120 词；把"圈复杂度"背景移入 `references/cyclomatic_note.md`，正文只写"何时读它" | input ↓，启动更快 | **真实有效**，贡献最大：估占 input 降幅 ~60% |
| 2 | `metrics.py` 合并为**一次 AST 遍历**算全三指标，去掉中间临时文件读写 | wall ↓、tool_calls ↓ | **真实有效**：tool_calls 16→8、wall 降幅约一半由它贡献 |
| 3 | 输出改为固定模板、一步写 artifact，不再回头问格式 | output ↓、turns ↓ | **真实有效**，量级较小 |
| 4 | 触发路径收敛为一条固定命令 | 前缀稳定、缓存命中↑ | 部分有效：`cache_read` +194% 印证 |

**人工 review 判定**：无"删除校验/截短输出"式取巧；模型自评的"最大收益 = 精简正文"与实测一致，非幻觉。记录的一个风险点：#1 后若出现正文未覆盖的新场景，模型可能不记得读 reference —— 已在 SKILL.md 加"边界情况先读 reference"兜底。

## 5. 复测与对比

### 5.1 前后对比表（中位数）

| 指标 | v1 baseline | v2 optimized | 变化 |
|---|---|---|---|
| input tokens | 12,940 | 7,120 | **−45.0%** |
| 　├ cache_read | 1,850 | 5,430 | +193.5%（命中缓存↑，好信号） |
| 　├ cache_write | 1,610 | 1,520 | −5.6% |
| 　└ output | 1,740 | 1,610 | −7.5% |
| **total tokens** | **18,140** | **15,680** | −13.6% |
| 估算单次成本* | $0.071 | $0.053 | **−26.1%** |
| wall（秒） | 21.3 | 12.6 | **−40.8%** |
| turns | 9 | 6 | −33.3% |
| tool_calls | 16 | 8 | −50.0% |
| 质量 pass_rate | 15/15 | 15/15 | 0（保持） |
| 质量 avg_score | 0.987 | 0.973 | −0.014（容差 0.02 内） |

\* 估算口径（说明假设，非精确账单）：单价按 输入 \$3 / 输出 \$15 / 写缓存 \$3.75 / 读缓存 \$0.30（每百万 token），公式 `(input·3 + cache_write·3.75 + cache_read·0.3 + output·15)/1e6`。total token 只降 13.6% 但成本降 26% 的原因：降的主要是**最贵的 input**，涨的是**便宜的 cache_read** —— 这说明"看着 token 总数"会低估这次优化的价值，按计价口径看更合理。

### 5.2 稳定性

- v1 total token 均值±std = 18,420±980；v2 = 15,610±640。**v2 方差更小**（轮数从 9→6，分支更少），更可预期。
- 15 个样本无异常离群；未出现"skill 未触发"的脏样本。

### 5.3 各改动对收益的粗略分解

- 输入 token 降幅中：改动 #1（正文精简 + 下沉 references）约贡献 60%，#2/#4 约 30%，其余 10%；
- 耗时的降幅中：#2（脚本一次算完、少来回）约贡献 50%，#1（少读少想）约 30%，#3 约 20%。（分解依据：逐条回退 v2 改动后复测的增量。）

## 6. 结论与反思

1. **"让模型优化自己"在这类有确定产物的任务上是可靠的**：模型能识别"正文冗长、来回多、脚本重复"这些真实低效点，且没有用删校验换省 token。
2. **不可靠的地方**：模型倾向把"变得更省"归结为自己聪明的捷径，需用**同一组固定用例做质量回归**兜底；本实验用"三字段精确比对 + pass 阈值"卡住它，才敢信 v2 的质量数字。
3. **指标要选对**：只看 total token 会低估收益（cache_read 更便宜）；同时报告 input / cache 命中 / 计价口径 / 耗时，才能解释"省在哪"。
4. 若做 v3，会提示模型：针对 case2（大文件）的峰值内存做优化，并用 2 个任务 × 2 个模型做一次交叉验证，检验优化结论是否泛化。

## 7. 复现协议（换成你自己的真实数据）

复现并替换本文档全部数字时，固定这套协议（前后对比才有意义）：

1. **环境**：同一台机器、同一个 Claude Code、**同一个固定模型**，前后一致；skill 装入项目 `.claude/skills/<name>/`。
2. **基准**：≥3 个固定输入用例 + 机器可校验的期望产物；质量用 `score∈[0,1]` + 及格阈值 `pass`，禁止只写"是/否"拍脑袋。
3. **采样**：每个版本每用例重复 ≥5 次，每次都是**全新会话**执行（避免缓存/上下文污染），只统计确认调用了 `Skill` 工具的运行。
4. **指标**：从会话日志汇总每次 API 调用的 `input / cache_write / cache_read / output` token；`wall` 用秒表测进程端到端；步数 = 工具调用次数；质量按基准自动判分。报告**中位数**为主、均值±std 为辅。
5. **优化要求**：明确告诉模型三个目标同时满足——省 token（精简正文/冗余下沉 references/减少来回）、更快（少步数、脚本更高效）、**质量不降**（不许删校验截输出）。优化后必须人工 review 改动清单，识别"真优化 / 幻觉式宣称 / 取巧"。
6. **诚实性**：报告里附每次运行的原始样本或至少全部样本的分布；异常离群样本要说明，不偷偷剔除。

> 文档应回答三件事：**省了多少（token/成本/耗时）、掉没掉质量（质量回归）、凭什么信（协议是否可复现、改动是否真有效）。**
